# 0005 — Web app: in-house i18n, webpack builds, Monaco from npm

**Decision (i18n):** `apps/web` uses a ~150-line in-house i18n layer (`src/i18n/`) instead of next-intl.
Messages live in `apps/web/messages/{en,sv}.json`; keys are type-checked (`MessageKey` is derived from
`en.json`, so `t("typo")` fails `tsc`). Formatting supports `{var}` and ICU-style
`{count, plural, =0 {…} one {# …} other {# …}}` via `Intl.PluralRules`. The locale comes from the
`forge_locale` cookie, else the best `Accept-Language` match, else English. Server components call
`getT()`; client components use `useT()` from an `I18nProvider` (root layout ships only the shared
namespaces; `/app` adds the rest). A unit test enforces en ⇄ sv key parity, identical placeholders and that
every literal key used in `src/` exists.

**Why:** two locales, no routing prefix needed (EU product, cookie-based switch), zero runtime dependency,
compile-time key safety, and no coupling to Next major-version churn (Next 16 here).
**Trade-off:** no message extraction tooling or rich ICU (select/number skeletons); add next-intl if we
grow beyond a handful of locales.

**Decision (build):** `next build --webpack` / `next dev --webpack` with
`experimental.extensionAlias`-equivalent `resolve.extensionAlias {".js": [".ts", ".tsx", ".js"]}`.
Workspace packages are TS source with ESM `.js` relative imports (ADR 0001); Turbopack in Next 16.4
cannot resolve `./x.js` → `./x.ts` inside transpiled workspace packages, webpack can.

**Decision (editor):** Monaco is bundled from npm (`monaco-editor` 0.57 ESM core + Monarch syntax
definitions, one base worker) — no CDN loader, so code never leaves our origin and CSP stays strict.
y-monaco's legacy import path is aliased to monaco's exported `editor/editor.api.js`.

**Cookies:** only `forge_session` and `forge_consent` are essential; `forge_locale`/`forge_theme` are
session cookies unless the visitor consents in the banner, then persisted for a year.
